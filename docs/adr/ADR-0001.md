# ADR-0001: 消息传输与事件接入选型

状态：Accepted  
日期：2026-08-04  
关联：ARCHITECTURE_PLAN §6、§9、§12

## 背景

业务系统通过 Transactional Outbox 产生审计事件，需要一条高吞吐、可重放的
传输链路进入审计账本。候选：Apache Kafka、Redpanda、NATS、直接 HTTP/gRPC。

约束：

- 写入必须至少一次投递且消费端幂等，不依赖网络端到端 exactly-once。
- 传输层不是长期合规归档；WORM 对象存储才是。
- 本机参考实现不能引入重依赖（本机没有现成 Kafka 集群）。

## 决策

1. 生产传输层采用 **Kafka 协议兼容实现（Apache Kafka 或 Redpanda）**，
   topic 布局遵循 `audit.events.accepted.v1`、`audit.events.ledgered.v1`、
   `audit.events.projection.v1`、`audit.events.archive.v1`、
   `audit.events.dlq.v1`、`audit.events.projection.dlq.v1`。
   最后两个 DLQ 分离：摄入 DLQ 的原像在 accepted topic（可由
   `audit-kafka-dlq-replay` 恢复），投影 DLQ 的原像在 ledgered topic
   （只能从 ledgered topic 重新驱动）。
2. 参考实现（当前仓库）接入路径为 **同步 HTTP/gRPC 直写 + Outbox Relay
   轮询投递**：业务事务内写 `audit_outbox`，`audit-outbox-relay` 消费并
   POST 到 `audit-api`。该路径在单节点上等价验证幂等、重试、死信语义，
   不引入 Kafka 依赖。
3. 生产切换时 relay 的 `DeliverFunc` 替换为 Kafka 生产者即可，Relay 的
   状态机（pending/delivered/failed、退避、死信）保持不变。

## 后果

- 优点：参考实现可独立运行与测试；Relay 语义与 Kafka 消费组一致。
- 代价：参考实现的吞吐上限低于 Kafka 路径，性能数字不能直接外推。
- 分区键：`tenant_id + aggregate_type + aggregate_id`，操作跨聚合时显式
  指定 `operation_id`；只按 tenant 分区会制造大租户热点。

## gRPC 接入边界澄清（2026-10-16，无权限规则变更）

- `WriteStream` 在首条消息读取前认证并检查 `audit:event:write`，随后每条消息仍重新
  验证；actor roles/payload 是事件数据，不能扩展签名 claims 或来源/租户绑定。
- 按 gRPC-Go `ClientStream.SendMsg` 语义，`Send` 的 nil 仅表示传输缓冲；服务端提前
  结束时可以返回 `io.EOF`，实际 RPC 状态须由 `Recv` 获取。已认证但无写权限的流
  必须最终 `PermissionDenied`、没有成功回执，也不持久化事件、receipt 或 Outbox。
  不能把首次 `Send` 必须 nil 当作授权 oracle，或接受任意发送错误代替最终状态断言。
- 回归在真实 bufconn 流的 trailers/Send/handler 边界同步，覆盖拒绝先到、发送先缓冲
  及并发拒绝；不通过 sleep、修改 JWT 寿命/生产超时或放宽权限来固定调度顺序。
  这是既有传输语义与测试 oracle 的校准，不新增接入能力、容量或业务执行。
