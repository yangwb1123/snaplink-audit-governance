# ADR-0011：发布确认与主动对账

状态：Accepted  
关联：ADR-0001、ADR-0003、ADR-0004；README「当前实现」

## 背景

租户写入闭包同时生成账本回执与 `ledgered_outbox`，但物理提交为
hot → cold → control。cold 已落盘、control 尚未落盘时崩溃，可能留下没有发布意图的事实。
只冲刷现存 Outbox 或等待客户端重试不能闭环。另一方面，发布成功后也会删除 Outbox，
因此「没有 Outbox」不是未发布的证明；`indexed/archived` 同样不是 Kafka 或 ClickHouse 确认。

## 决策

1. 发布顺序为：**broker 成功 → 持久发布确认 → 清理 Outbox**。
   确认绑定 `(tenant_id, event_id, stream_id, sequence, hash)`，重复确认保留首个时间；
   同一租户/事件的不同坐标失败关闭。确认失败不删除意图；确认已落盘而清理失败时，
   后续冲刷只做清理。跨副本同时发布或 broker 成功但确认未落盘仍可能重复，保持至少一次。
2. 确认是可重建的**交付元数据**，不是审计事实、投影确认或合规证据。
   不把逐事件历史堆进共享 control：PostgreSQL 使用迁移 007 的独立索引表
   `audit_publication_confirmation`；文件模式使用 `publications/<tenant>/<hash-prefix>/<event-hash>.json`。
   只保存坐标和确认时间，不复制载荷或搜索摘要。文件模式仍要求单写者。
3. API 后台在启动和周期轮次对账：每轮一个租户、最多 100 条 cold 记录，租户轮转；
   最新回执解析归档/热载荷后，未确认且没有意图的事件进入既有 Outbox。
   不将 `indexed`、`archived`、热淘汰或进程内修复集合当作发布确认。
4. 补发只用账本保存的事件，不使用重试请求提供的坐标/载荷。
   校验回执身份、重建内容摘要（精确 Schema、解密认证、旧摘要格式兼容）及链哈希。
   `EventDigest` 可引用保存的 `SourceDigest`，因此仅重算链哈希不足以发现内容损坏。
   缺失、损坏或无法认证的证据不补发，并计数；单个坏证据不阻断后续事件。
5. WORM 回读在释放存储锁后执行，一轮共享有界 deadline，不按对象重新计时。
   v2 页只复制该租户的有界 cold 记录；兼容的 v1 PostgreSQL 后端仍物化旧快照，
   需要规模化对账的部署必须先完成 v2 cutover。
6. 扫描游标是**易失、后端内的实时遍历位置**，不是固定证据快照或提交水位。
   SQL ID 分配不保证事务提交顺序，文件整体兼容写入也可能重排记录，因此完成一轮必须
   回到零，重启也从零开始。首个 page 固定有限 `Through` 终点，持续写入不会让扫描
   永远追赶移动尾部而无法重扫。持久确认防止重复历史补发；轮转重扫发现迟到提交。
7. PostgreSQL 开启发布前必须先应用迁移 007；API 启动和 readiness 探测该表，
   缺失失败关闭，不自动建表。`-check-config` 仍保持无网络，不替代运行时探测。
   升级前没有确认的历史事件是「未知」，可能被至少一次重发；不能从旧状态伪造确认。

## 边界与后果

- 不修改事件回执或业务状态；回执 `indexed` 当前表示参考读路径可用，不表示 ClickHouse 已确认。
- 不需要客户端重试即可修复 cold 账本事实缺失的发布意图；若在 cold 提交之前只写了 hot，
  仍由既有幂等重试恢复，该残余窗口不冒充本批已解决。
- 活跃队列仍位于 control，确认历史独立。跨副本公平调度、投影确认/水位、固定快照查询、
  投影重建及确认元数据生命周期属于后续交付；不得将扫描结束报告为投影完整。
  确认只描述既有逻辑 ledgered feed 的历史交付，迁移/重建 broker 目的地必须另行受控
  重驱投影，不能据旧确认声称新目的地已完整。
- 确认文件/表应与状态一起备份。只恢复账本而丢失确认会重复投递，不会抹掉账本或产生业务副作用。
  回滚可保留新增表和文件；旧版本忽略它们。不得为省空间删除尚未核对的证据或伪造确认。
- 可观测性使用无标签原子计数：修复意图、扫描记录、证据失败、失败轮次；指标抓取不访问存储。
  这些是工作/故障计数，不是不同事件数量或完成度证明。
