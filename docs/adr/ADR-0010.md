# ADR-0010: API/worker signer and archive consistency key

状态：Accepted（已实现）
日期：2026-08-28
关联：`docs/design-fail-closed-cross-process-consistency-key.md`、
`internal/runtimeconfig`、`checks/consistency_key.py`

## 背景

`audit-api` 与 `audit-governance-worker` 独立解析签名和归档配置。各自的
配置可能都通过本地校验，却因 Vault Transit key、HMAC/Vault 方案、S3 桶
或本地目录漂移而无法共同验证同一条证据链。原有 `-check-config` 还包含
不同的外部预检：worker 会探测归档目标，API 会校验 gRPC listener，因此
不能把它作为离线一致性比较器。

## 决策

1. `SigningArchive.ConsistencyKey()` 返回稳定的
   `algorithm|s3:<bucket>` 或 `algorithm|file:<dir>` 标识。HMAC 使用规范
   token `HMAC-SHA256`；Vault 使用已有的
   `vault-transit:<Transit key name>` 算法描述。签名密钥、加密密钥、Vault
   token 和 S3 凭据永不进入 key。
2. 方法只解析 signer、检查 S3 配置分支，不做 I/O 或构造归档 client；其
   partial-S3 判断与 `Archive()` 的 OR/partial-error/endpoint 分支一致。
3. 两个二进制在启动和成功的 `-check-config` 中追加 `consistency_key`，且
   是 ok 行的最后一个字段。新增 `-consistency-key` 纯模式只解析秘密和
   无网络的 transport 语法，不打开状态库、不认证、不探测 WORM、不绑定
   gRPC listener。
4. `checks/consistency_key.py` 只执行已构建的两个二进制，使用同一份环境
   的副本，并对缺失、失败、重复或不一致的 key 失败关闭。它由
   `python3 cli.py consistency-check` 暴露；`predeploy` 先 build 再比较。
   单元测试 mock 子进程，不把本地 `quality` 门禁绑定到外部基础设施。
5. `.github/workflows/quality.yml` 运行 `quality` 后运行网络无关的比较 smoke
   test。真实发布流水线必须将权威的合并部署值注入后再执行该命令。

## 评审发现处置

- Architect F-A、Security F-1、DevOps F1：通过独立
  `-consistency-key` 解决；worker 的 S3 readiness probe 不再阻塞一致性
  比较。
- DevOps F2、Security F-2：通过 built-binary checker、CLI wiring、缺失/非
  零/歧义处理和 mocked regression tests 解决。
- Architect F-B 及设计修正一：通过 `ConsistencyKey` 复用 `Archive()` 的
  partial-S3 分支解决，partial input 不再伪装成 file key。
- Architect F-C 及设计修正二：明确 `vault-transit:<keyname>` 包含的是
  Transit key 名称而不是 token；代码和测试均固定此非敏感语义。
- DevOps F3（没有仓库内 CI wiring）：通过 workflow 和 `predeploy` 命令
  解决。workflow 的开发 fallback 只验证 wiring，不代表生产配置。
- DevOps F0（没有生产 IaC）：明确拒绝在本方向内扩展。仓库 README 和本
  ADR 不宣称生产可部署；`deploy/*.verify.*` 仍是本地验证 fixture，生产
  IaC、秘密投递和权威 merged values 属于独立方向。
- Security F-3（endpoint host、transport posture、HMAC secret drift）：
  明确拒绝改变本方向的 v1 key 格式。FR-1/C3/I4 要求名称级、非秘密
  identity；把 secret fingerprint 放入 key 不可接受，endpoint/transport
  仍由 `Signer`、`Archive`、`Transport` 和完整 `-check-config` 各自失败关闭
  校验。该限制在测试、威胁模型和 release notes 中显式记录，不冒充后端
  身份证明。
- F7/F8：规范 HMAC token、API/worker ok 行的 API-only
  `jwt_secret_length` 差异以及新增末位字段均在 release notes/文档中记录；
  checker 不依赖固定字段数量。

## 后果

一致性 gate 能在 S3/Vault 不可达时发现两进程之间的方案、Transit key 名称、
桶名或目录漂移，同时不会泄漏 secret。它是 parity oracle，不是 correctness
oracle：两边同时使用错误但相同的配置，或只改变 backend host、retention、
HMAC secret，仍需依靠完整配置/秘密/传输流程发现。运行
`python3 cli.py consistency-check` 不能替代两个二进制的完整
`-check-config` 和运行时 readiness。

无 schema、路由或数据迁移；回滚为重新部署旧二进制。旧二进制不会输出该字段，
所以发布前应先把 API 和 worker 一起升级，再启用依赖 key 的部署 gate。
