## 编写约定

- 一条 `## YYYY-MM-DD — 祈使句标题`，一个用户可见的变更。标题写**做了什么**，不写
  “更新了 X 文件”。
- 正文先说行为变化，再说原因与验证手段；配置、阈值、失败模式的变化必须写明，因为它们
  决定运维动作（fail-closed 门禁、迁移顺序、告警口径都属于此类）。
- 同一天多次提交合并为一条，除非确实是互不相关的两件事。
- 只在主分支合入后写；不要把未合入的尝试记进来。
- 提案文档的验收条款会写“Add a `docs/release-notes.md` entry”——落地时写进当月文件即可。

## 什么时候不必写

- 纯内部重构（文件拆分、测试搬家、门禁脚本重构），前提是**没有**任何行为、配置或契约面
  变化。分不清时，写一条并注明“无行为变化”，读者过滤得掉，漏写的代价更高。
- 门禁阶段的新增与阈值收紧要写：它们会让别人的提交失败。
